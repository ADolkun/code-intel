# Docs check

`doc-check` checks the docs against the code: every link and anchor resolves, every repository path a doc names exists, every backend route and code symbol it names still exists, every `package.json` script, make target and mise task it runs is defined, every doc under the reachability `include` is reachable from its `root`, and the [agent instruction files](#agent-instruction-files) are well-formed. Run it in CI on every pull request and make it unconditional, because a code change can stale a doc that did not change. `doc_refs` answers the reverse question with the same extraction: which docs name a file, route or symbol.

**Scope.** The `[docs] scope` globs: every Markdown file they match, if git sees it (tracked, or untracked and not ignored).

**Per-directory rules.** A doc gets every check unless the first `[[docs.rules]]` entry whose `paths` match it names fewer, with a required `reason`: for historical or imported material, only `links` may be worth checking.

**Reference kinds.** Only what a doc writes as Markdown structure or code counts; a path or a name in plain prose is not checked.

| Kind | What counts | Fails when |
| --- | --- | --- |
| link | Relative Markdown links and images, and HTML `href`/`src`; external links and empty targets are skipped. | The target is not a file or directory git sees (`broken link`), or a `#fragment` on a Markdown target, or on a directory, matches no heading slug and no HTML `id`/`name` in it (`broken anchor`; the match is exact, case included). A directory link lands on its README.md, else its index.md. `/` is the repository root. A link with no path (`#heading`, `?plain=1`) is the doc itself. |
| path | A code span, or a fence line, naming a repository path: from the repository root, from `backend.root`, `frontend.root` or the backend package directory, or from the doc's own directory. A path whose first directory is a top-level directory but that is not there may also be the end of any deeper path (`skills/builder.py` written from `app/`), as a path whose first directory exists only deeper is; so a deleted root-level file whose path ends a deeper one passes. Line suffixes (`:12`, `#L12`, a pytest node id such as `::TestX.{test_a,test_b}`), globs and `{a,b}` braces are understood: alternatives with `*` or `?` are one glob, which one matching file satisfies, while each alternative without one (`src/{a,b}.py`) names a file that must exist; a brace pattern of more than 256 paths is `skipped`. A path that leaves the repository is `not_checked`. A `..` in a command is read from the repository root and from the doc's directory, and is `not_checked` unless the directory it names right after the `..` is there (`../scripts/gone.sh` with `scripts/` present), since the command may run beside a sibling checkout. After a `cd <dir>` earlier on the line (outside a closed `( )` subshell), a command's paths are read from that directory, taken from the repository root and from the doc's directory; they are `not_checked` when the `cd` names no literal repository directory (`cd ..`, `cd $APP`, a directory that is not there). In a fence only paths whose first directory is a top-level repository directory count, so a shell transcript or a sample stack trace is not checked line by line. | No such file or directory (`stale path`). Placeholders (`<name>`, `{x}`, `...`) and example names (`my_…`, `example…`) are skipped. |
| route | `METHOD /path` in a code span, a fence line or prose, and a code span that is only `/path` when its first segment (after an optional configured prefix) is a route root: the root of a live or unmounted backend route, of a frontend page, of FastAPI's own pages (`/docs`, `/redoc`, `/openapi.json`), or of a `METHOD /path` with an upper-case method (or WebSocket) in any doc whose rule checks routes. In prose the method must be upper case or WebSocket, so English such as "get" before a path is not read as a route. Every parameter syntax matches (`{id}`, `:id`, `[id]`, `<id>`), and a mention with or without a configured prefix matches. A path that opens with an ellipsis (`POST .../checkout`) names the end of a route: it passes as `suffix` when exactly one live route of a compatible method ends with those segments. Any other `...`, `${` or `{{` in a path is a placeholder and is skipped. | No live route fits (`route not found`), including one only a plain word filling a parameter would fit, unless a frontend page has exactly that path; only another method serves it (`route method differs`); or only a router the app does not mount does (`route not mounted`). A route tail fails the same ways, and when live routes at two or more paths end with it (`route not specific`). Blind spot: a root that the docs only ever name as a bare `/path` is skipped once its last route is gone, because nothing declares it a route root any more. |
| symbol | A code span that is a whole identifier, a dotted name, a call with empty parentheses or a JSX tag. | It is a CamelCase name, a name starting with an underscore, a call, a JSX component or `Class.attr` where `Class` is a Python class the symbol index holds, and the symbol index defines it nowhere, no tracked Python module whose dotted path ends with its qualifier binds it at top level (`pkg.errors.AuthState` passes when `pkg/errors.py` imports `AuthState` or lists it in `__all__`; `pkg` is `pkg/__init__.py`, and `test_widgets` is also `tests/test_widgets.py`; a star import of a tracked module brings its `__all__`, else its public names; an absolute one resolves only from the repository root, `src/` or `backend.root`), and no tracked code file uses it as an identifier (`symbol not found`). Python is read with `ast`, so a name left only in a comment or docstring does not count. The config file is not code here (an ignore entry's text would otherwise resolve itself). Other names (`snake_case`, `UPPER_SNAKE`, a dotted permission string) that resolve nowhere are `unresolved`, which never fails, and so is a qualified name of a module that may bind names at run time (a module `__getattr__`, or a star import of a module that is not tracked, is ambiguous or builds its `__all__` at run time). |
| command | A command in a code span or in a fenced shell block (info string empty, `sh`, `bash`, `shell`, `zsh`, `console` or `shell-session`), never in prose, that runs a `package.json` script (`npm run`/`run-script`/`rum`/`urn`, `npm test`/`t`, `npm start`, `npm stop`, `pnpm run`, `pnpm <name>`, `yarn [run] <name>`, `bun [run] <name>`), make targets (`make`/`gmake`, one reference per goal) or mise tasks (`mise run`/`r`/`tasks run`, several joined by `:::`, and `mise <name>` when the name has a `:` or starts with `//`). A directory comes from `cd <dir> &&` (or `;`, `\|`) earlier on the line, outside a closed `( )` subshell, or from `--prefix` (`npm -C`, also in a bundle such as `-sC`), `-C`/`--dir`, `--cwd`, `make -C`/`--directory` or `mise -C`/`--cd`. A directory is taken both from the repository root and from the doc's directory, and the name must be in one of those directories' definition files; a directory with none is `skipped`. Without one it may be in the repository root's, the doc's own directory's or (scripts) any `package.json` under `frontend.root` (none without `[frontend]`): if only another file defines it, it is `not_checked`. Make reads the first of `GNUmakefile`, `makefile`, `Makefile` and its rule lines in every conditional branch; of the special targets only `.PHONY` makes its prerequisites goals, and a target-specific variable line (`t: X = 1`) defines nothing on its own. Mise reads the config file names mise 2026.11 reads (`mise.toml`, `.mise.toml`, `mise/config.toml`, `.config/mise/config.toml`, `.config/mise/mise.toml`, their `.local` variants, `conf.d/*.toml` and the rest), file tasks under `mise-tasks/`, `.mise-tasks/`, `mise/tasks/`, `.mise/tasks/` and `.config/mise/tasks/` (unless the directory's config declares `[task_config] includes`, which replaces them), local includes and aliases. A file task's name drops only a script extension (`build.sh` is `build`, `notes.md` stays `notes.md`). An environment config (`mise.<env>.toml`) counts only when the command selects it (`MISE_ENV=<env>` or `-E <env>`); a task only it defines is `not_checked`. Without a root `monorepo_root` (or `experimental_monorepo_root`) a task name is looked up in the configs from the repository root down to where it runs, and `//path:task` and `:task` are `not_checked`. With one, mise's monorepo rules apply: a name or `:task` is looked up only in the project the command runs in (the nearest directory with a mise config, or with file tasks when `config_roots` lists it); `//path:task` only in `path`'s own files, when `path` is a config root (`[monorepo] config_roots`, single-level `*` globs; a `**` entry is ignored, as mise ignores it; every directory with mise files without the list) or the command runs in or under it; and `path:task` (after `[monorepo.path_aliases]`, `path` without `/`) also as `//path:task` from the root project, or from inside `path`. **The verdict is the one a fresh checkout gets on a clean machine**: user and system mise config, files above the repository root and environment variables (`MAKEFILES`, `MAKEFLAGS`, `MISE_ENV`, `MISE_*_CONFIG_FILE`) do not count; a goal that names an existing file or directory in another letter case is `not_checked`, since a case-insensitive file system finds it. A form whose outcome the files cannot settle is `not_checked`, with the reason: yarn and bun (they also run a binary of that name), `pnpm <name>` and `pnpm test`, `--if-present`, workspace and filter runs (`-w`, `-ws`, `--workspaces`, `-r`, `--filter`), `npm start` beside a `server.js`, `make -f`/`-I`/`--eval`/`-o`/`-W`/`-E` or an unknown option, a makefile with an `include`, a pattern, static pattern or suffix rule, `.DEFAULT`, `define`, `$(eval)`, `vpath`/`VPATH` or a target name it cannot expand, a goal a file of that name (or a built-in rule's source such as `prog.c`) may satisfy, a mise option other than `-C`, `-q`, `-v`, `-y`, a `node:` or `./path` task, and a mise file with a remote or templated include, `[task_templates]` or `extends`. Also `not_checked`: a command run where the runner has no file (no makefile, `package.json` or mise config in the repository root or the doc's directory, as in an autotools or `Makefile.PL` flow); a directory outside the repository or not written literally (`cd ..`, `~/x`, `$APP`, `-C /opt/x`), and every line of a fence after one that runs `cd`, `pushd` or `popd`; an option the reader does not know before the name; after an npm script name, a long option that may abbreviate one that changes resolution (npm reads `--if-pres` as `--if-present`; `--coverage` is only npm config and is ignored, and pnpm passes everything after the name to the script); a variable the command sets (`PREFIX=x make …`, `env X=…`, `make X=…`, `make -e`, an earlier `export`) when the makefile names targets with variables, and `MAKEFLAGS`/`MAKEFILES`, `MISE_*` (but `MISE_ENV`) or `npm_config_*` set on the command; a tracked `.npmrc` that sets `if-present`; and an unprompted fence line that names several make goals, which may be a `make help` listing. In a fence where any line starts with a `$` or `%` prompt, only the prompt lines are commands (a `#` line is a comment); continued lines (`\`) are joined and heredoc bodies skipped. Placeholders, wildcards and example names (`<script>`, `$X`, `*`, `//...:task`, `my-…`, `your-…`, `example`, `target`, `task`, `script`, `script-name`, `task-name`, `target-name`, and an undefined ALL-CAPS name such as `TARGET`) are `skipped`. A definition file that cannot be read, decoded or parsed (including TOML 1.1 that Python's reader rejects, and nesting too deep to parse) makes the references that depend on it `not_checked`, with the file and the error; it is not a run diagnostic. A tab-indented `include` or `$(eval)` makes a makefile's targets unknown, and a variable assigned twice anywhere, or in a conditional, leaves the target names built from it unknown, and so do variables that expand to more than 100,000 characters in all; a suffix rule counts only for GNU make's default suffixes and `.SUFFIXES` additions. Only tracked definition files count, wherever they are (a tracked `dist/Makefile` too); a repository with no file of a runner has no references for it. | No tracked file of the runner defines the name and every one of them could be read and holds a provable set (`command not found`). |

Two file-level findings complete the list: `orphaned doc` for a doc matching the reachability `include` that no chain of links from `root` reaches, and `unused ignore entry`.

**Statuses.** A reference that fails is `missing`, `anchor_missing`, `method_differs`, `weak_param`, `unmounted` or `ambiguous` (a `.../tail` that several live routes or pages end with). Every other status passes: `ok`; `prefix` and `suffix` (a bare path that is the start or the end of a live route, or a `.../tail` that ends one); `frontend` (a frontend page, route handler or public file); `framework` (`/docs`, `/redoc`, `/openapi.json`); `local_only`; `ignored`; `skipped` (external, placeholder or example); `not_checked`; `unresolved`.

**What git sees.** A file exists for the check when git tracks it or lists it as untracked and not ignored. A tracked file deleted from the work tree but not staged does not exist. The listing also runs inside every initialized submodule, each with its own ignore rules, and with `core.ignorecase=false`, so it matches case-sensitively as on a Linux CI checkout. Symbols, code words, backend routes, frontend pages, diagnostics and route limitations that come from an untracked or ignored file are ignored, so a local run gives CI's verdict.

**Local-only paths.** A path with a directory that never reaches git (`.venv`, `node_modules`) or one git ignores (`.env`, generated code) is `local_only` and passes: it exists on a developer's machine and nowhere else, so neither side can check it. Blind spot: a stale path that a broad `.gitignore` pattern happens to match (`*.log`, `build/`) is `local_only` too.

**Submodules.** Links and paths into a submodule that is not checked out are `not_checked`, with a `submodule_missing` limitation. Symbols are never `not_checked` for a missing submodule.

**Pages.** Without Node or TypeScript, `react-router` pages are unavailable and a bare path that only a page could satisfy is `not_checked` (`frontend_pages_unavailable`); install the toolchain in the job (`stack-intel setup`) to check them.

**Partial configs.** Without `[backend]` there are no backend routes to check a route against, and the docs probably name the API of a backend that lives elsewhere, so a `METHOD /path` mention, and a bare path that no frontend page satisfies, is `not_checked` (detail `no [backend] table`); a bare path a page satisfies is still `frontend`. Without `[frontend]` there are no pages, so a bare path under a backend route root that matches no route stays a `route not found` finding, as with `[frontend.pages] kind = "none"`. Python definitions come only from `backend.root` and TypeScript definitions only from `frontend.root`, and path roots only from the sides configured; names still resolve through the code words of every tracked code file. The report carries one `not_configured` limitation per missing side, when some doc in scope runs a check that side would feed (`routes` for `[backend]`; `routes` or `symbols` for `[frontend]`). Without `[docs]`, `doc-check` checks only the agent files and reports a `not_configured` limitation saying no docs were checked; with no agent files either it exits 2.

**Library routes.** A route installed code adds is live once the [library capture](analysis.md#library-routers-and-dependencies) has it, so a doc naming it resolves like any route, and a lookup of the route names the repository `include_router` that mounts it and where the library defines the handler. Without a capture entry it is missing from the analyzed list, so a doc naming it fails with `route not found`, and the run prints the `unresolved_include` [limitation](tools.md#limitation-kinds) after the findings. Giving every such doc an ignore entry is the intended fix, since treating the limitation as "not confirmed" would leave the route check unable to fail.

**Ignore entries.** An ignore entry suppresses the failing references of one kind in one file whose text, as written, equals `text`, and needs a `reason`. A link's text is its target percent-decoded, and the entry may give it either way. An entry that suppresses nothing is itself a finding (`unused ignore entry`), so entries go away with the drift they covered. An entry for a reference that cannot be checked locally still counts as used.

**Fixing a finding.** The line names the doc, the line and the reason:

- `broken link` / `broken anchor`: point the link at the file or heading as it is now.
- `stale path`: write the current path. An illustration that is not a real file gets a placeholder (`<path>`) or an example name.
- `route not found`, `route method differs`, `route not mounted`: take the route's URL and method from `route_match`, never from the decorator, which omits mount prefixes.
- `symbol not found`: use the current name. A name that was deliberately removed and that the doc still mentions goes in plain text, not a code span.
- `command not found`: run a script, target or task the repository defines (the detail names the files read), or add it. A command that is deliberately not this repository's gets an ignore entry with `kind = "command"`.
- `orphaned doc`: link it from the reachability root or from a page reachable from it.
- `unused ignore entry`: delete the entry.

Add an ignore entry only when the doc is right and the check cannot see it, and say why in `reason`.

```
$ stack-intel doc-check
docs/items.md:7: route not found: POST /items/import (only /api/items/{item_id} fits, by a word in a parameter)
doc-check: 1 finding in 2 docs (7 references, 6 checked); 0 agent files
```

## Agent instruction files

The docs check also validates the instruction files Claude Code and GitHub Copilot load, with or without an `[agents]` table, and prints their findings as `path:line: message` beside the docs findings; the summary line ends with the number of agent files read (`; A agent files`). Only git-visible files at the repository root's conventional locations count; a nested `.claude/` directory (a sub-project launched on its own) is not read. Files are read as UTF-8, with undecodable bytes replaced as the agents replace them. A default finding states what goes wrong for a named reader (Claude Code, Copilot CLI or VS Code), and only where that reader's behavior is known; behavior that is not known is never a finding.

| Location | Read by | Checked |
| --- | --- | --- |
| `.claude/rules/**/*.md` (a symlinked `.claude/rules` inside the repository is followed) | Claude Code, Copilot CLI | Frontmatter, when line 1 is `---`, that Claude Code cannot read (see **Frontmatter** below), a `---` inside a value that ends Claude Code's frontmatter before `paths`, and a non-empty `paths` with no string glob left (`paths: 123`, a map, `[3, 4]`): each makes Claude Code load the rule for every file. A `---` inside the `paths` value is reported when what is left before it matches nothing. Each `paths` glob matches at least one git-visible file. |
| `.claude/agents/**/*.md` | Claude Code, Copilot CLI | With a `name`: frontmatter Claude Code can read, a non-blank `description`, a name of at most 256 characters that does not start with `-` and has no `:`, unique among the subagents Claude Code loads. A file without `name` is documentation and is not checked. |
| `.claude/skills/<dir>/SKILL.md` | Claude Code, Copilot CLI | Frontmatter Claude Code cannot read (it loads the skill without it). The directory is not `synced` and the name is not `anthropic-skills` or `anthropic-skills:*` and has no `<`, control, zero-width, bidi or private-use character, which Claude Code does not load. |
| `.agents/skills/<dir>/SKILL.md`, `.github/skills/<dir>/SKILL.md` | VS Code | Nothing by default. VS Code 1.147.0 collects YAML errors instead of failing, reads an unclosed header to the end of the file, and loads a skill with a missing or mismatched name under its folder name, so a parse failure and the Agent Skills rules are reported here only under `strict`. |
| each `skill_dirs` entry | Agent Skills | Frontmatter is present and parses. `name` is 1-64 lowercase letters, digits and hyphens, with no leading, trailing or double hyphen, and equals the directory. `description` is a non-blank string of at most 1024 characters. |
| `.github/instructions/**/*.instructions.md` | Copilot | When the frontmatter parses: each `applyTo` glob matches a file, and `excludeAgent` is `code-review`, `cloud-agent` or `coding-agent`. |
| `.github/agents/**/*.md` | Copilot | The base name uses only ASCII letters, digits, `.`, `-` and `_`. Parsed frontmatter has a non-blank `description` and a `target` of `vscode` or `github-copilot`. |
| `.github/hooks/*.json` | Copilot CLI and cloud agent | JSON object, `version` 1, `hooks` an object whose every value is an array (otherwise Copilot rejects the whole file). |
| `.mcp.json`, `.github/mcp.json`, `.vscode/mcp.json` | Claude Code and Copilot CLI; Copilot CLI; VS Code | A file that is not blank parses as JSON (JSONC for VS Code). `.mcp.json` is `{}` or has an `mcpServers` object; `.github/mcp.json` has one or is a bare map of servers; `.vscode/mcp.json` keeps them under `servers` and declares every `${input:ID}` in `inputs`. Every server is an object with a `command` or a `url` (VS Code infers a missing `type`); for Claude Code and Copilot CLI a server with no type (or `stdio`, `local`) has a `command`, and one with only a `url` and no type is a finding (it is read as a stdio server and skipped); `http`, `streamable-http`, `sse` and `ws` servers have a `url`; `args` is a list of strings; `env` and `headers` are objects. JSON the parser cannot hold (a 5000-digit number, nesting 100,000 deep) is skipped. |
| `CLAUDE.md` and `AGENTS.md` at any depth, `.claude/CLAUDE.md`, `.github/copilot-instructions.md` | Claude Code, Copilot CLI | Every `@path` import resolves, relative to the file or to the repository root. Only `@` at the start of a text run or after whitespace counts, outside code and table cells and not escaped as `\@`, followed by a path ending in `.md`, or starting with `./` or `../` and naming a Markdown or text file or one with no extension; a `#fragment` is dropped. Quoted, absolute and `~` paths, a target git ignores and `@word` mentions are not checked. |

**Frontmatter.** Claude Code (as observed in Claude Code 2.1.328) ends the frontmatter at the first `---` after the opening line, even inside a longer run such as `-----`. YAML that does not parse is retried once: each top-level `key: value` line whose value holds `{`, `}`, `[`, `]`, `*`, `&`, `#`, `!`, `|`, `>`, `%`, `@`, a backtick or `: ` is double-quoted, unless the value is already in matching quotes or is a `[...]` list that parses on its own, and leading tabs become spaces. Only a failed retry drops the frontmatter, so `paths: **/*.ts` and `description: Use this agent when: the user asks` are read, while a block-list item such as `  - **/*.ts` is not quoted and breaks the file. A `[...]` value that is not a list on its own (`paths: [src/api/**, {lib]`) is quoted into one string; when no piece of that string matches a file, the finding names the line that made the YAML invalid and how to fix it. Because the block ends at the first `---`, `description: Backend --- API layer` above `paths` drops `paths`. A repeated key keeps its last value. Values are read as YAML 1.2 reads them: only `true` and `false` are booleans and dates stay strings. Frontmatter with no key-value lines (a `---` rule above prose) has no keys, and an unclosed one is not frontmatter. Frontmatter the YAML library cannot load although it may be valid (`!!float abc`, a 5000-digit number, nesting 3000 deep), before or during the retry, is not a default finding.

**Globs.** A glob is reported only when it matches no git-visible file or directory under the most lenient reading a known reader uses: case-insensitive, folded per character as Python's `re` folds it, with range bounds kept in their case (`[B-a]` matches `x`, `[A-z]` matches `_`); `**/` prepended unless the pattern starts with `/` or `**/` (VS Code); a trailing `/**` also matches the directory itself; `./` stripped; brace options trimmed (`{ js, ts }`); `[...]` tried as a class and as a literal (for directories such as `[id]`). A comma-separated string is split into globs reported one by one; in a list, nested lists are flattened, non-strings dropped, and each item is also split on commas and reported only when no piece matches. A glob is also not checked when something the reader may see could match it: its literal directory is a symlink, lies under one, or exists on disk untracked, or git ignores its directory or the paths it would match (`gen/**/*.ts` with `gen/` ignored, `**/.env*`). Negation, extglobs, backslash escapes, POSIX classes, brace ranges, braces or brackets holding a comma inside a comma-separated string, and globs past the work bound (longer than 256 characters, more than 64 brace expansions) are not checked. Matching never backtracks: a glob with more than two wildcards runs as an automaton over each path once, built from the same one-character tests as the regex.

**Never reported by default:** unknown frontmatter keys, a missing `paths` or `applyTo`, an empty `paths` (`""`, `[]`, `[""]`), a `paths` list with non-string items beside a string glob, an `applyTo` value of another shape, `applyTo` in `.claude/rules`, instruction files without frontmatter, `.mcp.json` servers without `tools`, a Claude Code skill whose name differs from its directory, subdirectories under `instructions/`, `rules/` and `agents/`, YAML that does not parse in `.github/instructions` and `.github/agents` (Copilot CLI recovers the keys), frontmatter Claude Code's retry reads, a skill frontmatter that does not parse in `.agents/skills` and `.github/skills`, a repeated key, YAML 1.1 words such as `yes` and `on`, one skill name in two roots, a blank MCP config, and `.github/prompts`, `.claude/commands` and settings files.

**`strict = true`** adds: every `.claude/rules` file has frontmatter with at least one `paths` glob, a `paths` that is a non-blank string or a list of non-blank strings, and no `applyTo`; `applyTo` is a string or a list of non-blank strings; the Agent Skills rules apply to every skill root; every directory directly under a skill root holds a `SKILL.md`; frontmatter that is not clean YAML is reported with what the reader does about it (`invalid YAML frontmatter: ...; Claude Code recovers by quoting the value`), as is frontmatter the YAML library cannot load (`frontmatter could not be checked`) and frontmatter that is not a mapping of keys; a repeated key is reported (`the last value wins`).

**Instruction map.** With `instruction_map`, the section under `heading` in `file` lists ``- `label`: `glob`, …`` lines that must equal the `.claude/rules` files' stems (`web/forms` for `.claude/rules/web/forms.md`) and their `paths` exactly; a comma-separated `paths` string counts as its globs.
